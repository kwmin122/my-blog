## Objective

Install the MDX processing pipeline and stand up the `/text/{slug}` canonical route so that dropping a `.mdx` file into `content/posts/` automatically produces a fully-rendered, SEO-indexed HTML page with zero manual route configuration. This slice also creates the shared slug-discovery utility and the zustand world store slice that Wave 2 depends on, making those dependencies available before the world route is wired.

## Capabilities

- **CORE-03**: `/text/{slug}` serves pure HTML/MDX with no 3D — canonical for search engines.
- **CONT-01**: Author writes one `.mdx` file; both routes are generated automatically at build time.

## Technical direction

The MDX processing pipeline is a thin layer on top of Next.js App Router's static generation. `@next/mdx` installs as a config wrapper around `next.config.ts` — the existing `webpack` alias for `three/webgpu` and the `turbopack: {}` block must be preserved inside `nextConfig`; only the outer `export default` changes from `nextConfig` to `withMDX(nextConfig)`. The `pageExtensions` addition tells Next.js to treat `.mdx` files as page components, but `.mdx` files must live only in `content/posts/` (never in `app/`) to avoid creating unintended routes.

The `lib/posts.ts` utility is server-only Node.js `fs` code. It is the single source of truth for slug discovery. Both the text route and the world route (Plan 02-02) import `getPostSlugs()` from here. The function reads the `content/posts/` directory at build time; no runtime filesystem access is needed.

The `lib/worldStore.ts` zustand store is created in this wave even though it is consumed in Wave 2. This sequencing prevents a circular dependency: Plan 02-02's `WorldPostPanel` client component imports from this store, and the store must exist before that component is written. The `postOverlay` slice holds only string data (`slug`, `title`, `excerpt`) — no MDX components or React elements enter the store, which is what enforces the CORE-04 constraint at the data layer.
