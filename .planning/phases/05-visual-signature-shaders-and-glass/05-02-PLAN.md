## Objective

Lock the design palette down to a single base tone and three dopamine accent values by adding `baseTone` and `accent` named exports to `tokens/tokens.ts`, and shipping a dev-only `assertLightColor` utility in `lib/colorAudit.ts` that fires a console warning when a Three.js scene light's color falls outside the locked palette range. This establishes the palette contract that all subsequent phases must respect and gives the developer an immediate runtime signal when a stray color is introduced.

## Capabilities

VIS-03 — Single base tone + dopamine accent palette lock; dev-time saturation guard

## Delivery scope

- `tokens/tokens.ts` gains two new named exports at the bottom of the file:
  - `export const baseTone = tokens.color.base` (string alias satisfying "baseTone 1값" success criterion)
  - `export const accent = { neon: tokens.color.accentNeon, sky: tokens.color.accentSky, light: tokens.color.accentLight } as const` (satisfying "accent.* 3값" success criterion)
- New file `lib/colorAudit.ts`: exports `assertLightColor(color: string | THREE.Color | { r: number; g: number; b: number }, label: string)`. In `process.env.NODE_ENV === 'development'` only, converts the color to HSL, and warns in the dev console if the chroma (saturation) value is above a computed threshold that would indicate a color outside the base ± accent range. In production, the function is a no-op. The function does NOT import three.js — it accepts a plain RGB object or a CSS color string, keeping it usable without a Three.js context.

## Verification intent

- Open `tokens/tokens.ts` and verify `baseTone` and `accent` are present as top-level named exports.
- In a Node REPL or browser console, import `baseTone` from the tokens module and confirm it equals `'oklch(0.12 0.01 240)'`.
- In a Node REPL, import `accent` and confirm it has keys `neon`, `sky`, `light` — exactly three.
- Trigger `assertLightColor` manually in dev console with a deliberately over-saturated color such as `'oklch(0.7 0.40 200)'`. The console should print a `[colorAudit]` warning identifying the label and the offending chroma value.
- Call `assertLightColor` with `tokens.scene.sunlight` (`'#fff8e8'`). No warning should appear — this color has near-zero chroma.
- Call `assertLightColor` with `tokens.color.accentNeon` (`'oklch(0.82 0.25 140)'`). No warning should appear — this is a registered accent.

## Technical direction

`tokens/tokens.ts` is excluded from the `local/no-hardcoded-hex` ESLint rule, so the existing hex values in `tokens.scene.*` remain valid. The two new exports are simple re-aliases of already-defined values — no new color literals are introduced. Place them after the existing `export type` declarations so the file's structural sections remain clear.

`lib/colorAudit.ts` must avoid importing Three.js classes (that would create a server-side bundle dependency on the 3D renderer). Instead, accept `string | { r: number; g: number; b: number }`. For string inputs, parse CSS `oklch(L C H)` directly with a regex (extract C as chroma). For Three.js `Color` objects (duck-typed: has `.r`, `.g`, `.b` in 0–1 range), convert to HSL using the standard RGB-to-HSL formula and treat HSL saturation * lightness complement as a proxy for chroma. The acceptable chroma ceiling is derived from the accent palette: `accentNeon` has chroma `0.25`, so any value above `0.28` (a small tolerance margin) triggers the warning. This constant should be a module-level `const MAX_CHROMA = 0.28`.

The warning message format: `[colorAudit] "${label}" chroma ${chroma.toFixed(3)} exceeds MAX_CHROMA ${MAX_CHROMA} — add to accent palette or reduce saturation.`
